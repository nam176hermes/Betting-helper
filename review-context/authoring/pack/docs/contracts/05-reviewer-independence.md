# Review launch, trust, isolation and deterministic aggregation

Host review authority is an explicit external actor. Its Ed25519 private key is /home/thenam176/.config/hybrid-discovery/review-authority/ed25519-private-key.pem (0600); public record is ed25519-public-key.json (0644) in the same directory. Key bootstrap is a human-authorized command, not candidate replay. Public record fields: schema_version=review-public-key/v1, key_id=key:ed25519:SHA256(raw_public_key), role=HOST_REVIEW_AUTHORITY, public_key_b64url (32-byte unpadded canonical encoding), trust_epoch (nonnegative integer). Private material never enters candidate, pack, workspace, reports or logs.

Signing uses RFC8785 JCS bytes of the closed record without signature and its derived authorization_id/receipt_id. Authorization ID uses SHA256(b"HD636/REVIEW-LAUNCH/ID/v1\0"+JCS); signing domain is b"HD636/REVIEW-LAUNCH/SIGN/v1\0". Receipt uses corresponding REVIEW-RECEIPT domains. Ed25519 verifies canonical 64-byte signatures. Launch and receipt bind host_boot_id read from /proc/sys/kernel/random/boot_id, trust_epoch, explicit public-key ID, signed inputs, role, serial, expiry and exact workspace. No guessed or self-declared trust key is accepted.

Consumption/revocation state is /home/thenam176/.config/hybrid-discovery/review-authority/state.sqlite, host-only 0600. BEGIN IMMEDIATE plus unique(authority_key_id, one_use_serial) consumes before creating a workspace. Commit consumption before launch; crash burns serial. Revocations and current trust_epoch are checked at prepare, execute, finalize and aggregate. Reboot mismatch invalidates all receipts from the previous host boot. Rotation invalidates old trust_epoch. The state database and host key are never mounted in reviewer processes.

Configs give exact distinct review-a/review-b workspace, scratch and output roots. Each namespace binds final runtime and final pack read-only at their original absolute paths; shared command cwd is therefore a read-only mount, not a shared writable workspace. Authoring and peer output are absent. Host launcher prepares offline scratch Python environments before entering namespace, with fixed UV_PROJECT_ENVIRONMENT per role; package installation is frozen, offline, and dependency projection must equal the qualified lock. Scratch/cache output is separated from allowed review outputs. The private key/host state are not accessible inside the namespace. Bubblewrap unshares user, PID, mount and network namespaces; temporary HOME and /tmp reside under role scratch. Fail closed if isolation cannot be established. No generic host-command escape.

Prepare consumes authorization and creates attested mounts. Execute revalidates the consumed authorization, enters that existing namespace and runs only configured leaf command IDs; it does not consume again or recreate workspace. Exact setup/execute/finalize commands are wired in P10 task cards. The host records command IDs, argv/cwd/env/input roots, actual exits and stdout/stderr hashes. commands_executed_root is SHA256(b"HD636/REVIEW-COMMANDS/v1\0"+JCS(entries sorted by command_id)). Duplicate, missing, skipped or extra commands fail. Freshness is checked using trusted host time: launch lifetime exactly 14400 seconds, maximum duration 14400 seconds, aggregation no later than 3600 seconds after the later review completion, and before either launch expiry.

A human starts a fresh Codex session per role with the exact prompt file and signed read-only inputs, writes the review result in that role's output root, and attests HUMAN_FRESH_CODEX_SESSION. This is an explicit human input, not a fake executable prompt command or cryptographic model-independence proof. Finalize requires result schema validity, matching role/input hashes, no unexpected changed path and the host-issued execution chain. Missing human attestation yields HOLD. Automated mechanical checks cannot impersonate independent judgment.

Aggregation verifies both chains, public keys, boot/trust epochs, serial uniqueness, disjoint workspaces/outputs, identical pack/REPO0 input hashes and exact command roots. PASS requires both review outcomes PASS, no blocking finding, all required cybersecurity verdicts YES, REPO0 and implementation prerequisite flags YES. SAFE_TO_FREEZE_SCOPE0 is independent: NO remains valid with READY_TO_IMPLEMENT_DISCOVERY_PACK=YES. Any failed check yields REJECTED; unavailable/incomplete check yields HOLD; neither can emit readiness YES. Findings sort by severity CRITICAL, IMPORTANT, MINOR then finding_id; conflicting duplicate IDs fail. Result review_run_id is UUIDv5(NAMESPACE_URL, "hd634:"+SHA256(concatenated raw A-result, B-result, A-receipt, B-receipt SHA256 bytes in that role order)). content_hash is SHA256(b"HD636/REVIEW-RESULT/v1\0"+JCS(result without content_hash)). No current timestamp/random field enters result, so identical inputs produce identical aggregate bytes. Authority is always NONE.

The exact HOST_REVIEW_AUTHORITY_BOOTSTRAP argv is registered as external-bootstrap and has no automatic task consumer. The human must explicitly authorize and complete it before either P10 role starts. --initialize-if-absent creates only missing host key/state in the protected authority directory, verifies existing identity/modes, and never rotates/replaces a key or resets consumption. Those three external inputs have the sole creation actor HOST_REVIEW_AUTHORITY in the artifact source records and are not materialization prerequisites. Their absence is HOLD at review launch.

Each A/B authorization has exactly five READ_ONLY input_mounts: final runtime directory, final pack directory, and their external final ZIP, sidecar and seal-attestation files named in config.seal_inputs. source_root and workspace_mount are identical canonical absolute paths. For regular file mounts content_root_sha256 is SHA256 of the raw bytes; for directory mounts it is the registered governed/file-tree root. The host verifies all five before signing and again before prepare/execute/finalize; review processes receive those five inputs. Reject duplicate, omitted, replaced, symlinked or additional mounts, role/root mismatch and any writable input. No host signing key or state mount is added.

Execution receipts input_content_roots has exactly five entries, in the same array order as the signed input_mounts. Each value equals that mount content_root_sha256. Finalizer and aggregator reject missing, reordered, duplicate or substituted input identities; identical hash values for distinct inputs are permitted only when their signed paths differ. Authorization_id also binds the complete signed launch.

After consuming launch authorization and creating role scratch, host prepare runs preparation_command_ids in their configured order: role-specific Python sync (UV_PROJECT_ENVIRONMENT from config) and Node install. Copy exactly node_environment.project_inputs first, preserving relative package/workspace layout. The Node project has root and extension node_modules; bind each at the matching final-runtime path from dependency_mounts. Relative pnpm links then resolve inside those two readonly mounts under native Node ESM; do not use NODE_PATH or modify sealed source. These two dependency mounts are distinct from the five signed artifact mounts and derive exclusively from their signed frozen lock/package bytes. Verify pinned executable versions, installed package versions/integrities and reject missing/corrupt offline cache, lifecycle scripts, undeclared packages, external links and source/lock mutation. Missing offline material yields HOLD. No dependency tree is shipped as pack/runtime source.

Host records preparation commands separately from leaf review commands. preparation_commands_root in the signed execution receipt is SHA256(b"HD636/REVIEW-PREPARATION/v1\0" + RFC8785 JCS of actual ordered preparation command records with command_id, argv, cwd, exact environment, exit and stdout/stderr SHA256). The finalizer requires precisely the two configured successful setup records and readonly dependency mounts; the aggregator verifies their signed binding. Review command roots continue to cover exactly the role's leaf IDs.
