## Blocking findings

### V632-R01 — Governed-root algorithm contradicts the sealed evidence

`docs/contracts/00-sealing-and-attestation.md:9,18` specifies domain separators ending in `/v1`. Applying that exact algorithm to the 76 governed files produces:

`05da6370af2a16b4e01e7359bd3a286ae7d4c38ea1ae9a1ba7b284fa73dd1175`

`GOVERNED_CONTENT_ROOT.json:3-4`, both self-review records and the external attestation instead bind:

`50c7a356d98f2b47bdc992d0a67a9375b6a891aa5a02799c0826becc4c6bbaf5`

The latter is reproduced by changing both domain separators to `/v5`. Thus the bytes are mutually bound, but a fresh reviewer following the normative contract obtains a different root. Freeze one algorithm and rebuild the dependent evidence in a successor artifact. The internal self-review correctly avoids final manifest/ZIP hashes; that acyclic repair should be retained.

### V632-R02 — Candidate qualification requires future sealing and review evidence

`V632-P07-T02` requires every proof-matrix row to have passing executed evidence. The matrix includes `V631-C1.ACYCLIC_SEAL`, whose evidence is `.task-evidence/V632-P09-T02.json`, and `V631-C6.CYBERSECURITY_COMPLETE`, whose evidence is the final Review B execution receipt produced at P10.

P09 and P10 transitively depend on P07. There is no frozen rule selecting only evidence eligible at the current gate. Requiring the complete matrix at P07 therefore creates a cycle. Additionally, `VERIFY_V632_P07_T02` resolves `--evidence-root .task-evidence` under the runtime cwd, while task evidence paths are declared relative to the authoring task workspace; that mapping needs an explicit owner/layout contract.

The four requested gates have distinct names and an ordered main dependency chain, but those declarations do not repair the reverse evidence dependency.

Evidence: `docs/plans/p07-candidate-qualification.md:103`; `docs/registries/proof-coverage-matrix.v1.json:5,137,158`; `docs/registries/task-command-registry.v1.json`, command `VERIFY_V632_P07_T02`.

### V632-R03 — Materialization and release ownership still disagree

P01-T02 promises to create every planned internal path, and P01-T05 promises all release tooling before P06. Nevertheless, the ownership table assigns creation of `runtime/tools/create_zero_parent_repository.py` to P08-T02, `qualify_zero_parent_baseline.py` to P08-T03, `assemble_review_pack.py` to P09-T01 and `compute_governed_content_root.py` to P09-T02. None exists at the declared v6.2 baseline path.

Creating those files in P01 violates the declared creation ownership; waiting for their owners violates the early materialization contract. Other early stubs, including export and seal tools, are modified by P08/P09 tasks after P07 qualification, without a required requalification gate before their use. Mere stub existence is not tool qualification.

Assign early creation/implementation/qualification ownership explicitly, then make later export/seal tasks consume the qualified tools without silently changing the qualified candidate.

Evidence: `docs/plans/p01-complete-artifact-materialization.md`, P01-T02 and P01-T05; `docs/registries/artifact-ownership.v1.json:1323,1358,1366,1458`.

### V632-R04 — Referenced artifact ownership is incomplete

Every task's `exact_files` entry is covered, but that list is not the full consumer closure:

- `ISSUE_V632_P00_T05` consumes `pack/docs/registries/task-command-registry.v1.json`; no task or baseline mapping owns its creation at that location. BOOT0 copies the plan under `plan-input`, not under `pack`.
- All 46 crash rows require `runtime/tools/inspect_restart_state.py::inspect_restart_state`; the file has no creation owner and is absent from the v6.2 runtime baseline.
- All 14 cybersecurity command targets lack both an owner and a baseline source at the declared paths. This includes the eight Python security test files and six TypeScript security test sources corresponding to the compiled JS targets.
- All 59 `.task-evidence/...` artifacts are named by their tasks but omitted from the artifact registry. Their producers can be inferred from the cards, but the closed inventory and materialization classification do not capture them.

Extend ownership validation over command operands, registry references, generated files and evidence, rather than validating only `exact_files`.

Evidence: `docs/registries/task-command-registry.v1.json:1031`; `docs/registries/crash-harness-registry.v1.json:18`; full cybersecurity and artifact-ownership registries, compared against the baseline filesystem.

### V632-R05 — MIG0 has a named role, but no decision-complete synchronization contract

The migration contract names MIG0 as sole owner. Its actual rebinding table contains four broad string replacements with abstract `scope` labels; it does not contain the promised exact file scopes or replacement modes. It also does not freeze treatment of the inherited v6.2 paths and provenance-bearing migration inputs in the legacy scan; only review globs and one provenance receipt appear as explicit historical exceptions.

MIG0-T04 synchronizes and locks the normative bundle before P01-T03 creates many schemas/registries and P03/P04/P05 modify those artifacts. No subsequent MIG0-owned synchronization/lock refresh is scheduled. A fresh implementer must choose between stale vendor/lock bytes and an undeclared later synchronization operation. The sync command targets `runtime/vendor/hybrid-discovery-v6.3.2`, while the schema-reference registry expects an additional `docs/` component; the layout is not explicitly resolved.

Freeze exact transformations, path mappings and historical exceptions, and give every later normative change a deterministic MIG0-owned resynchronization point before qualification.

Evidence: `docs/contracts/02-successor-migration-rebinding.md`; `docs/registries/version-rebinding.v1.json:3,25`; MIG0-T04/T05 commands; P01-T03/P03-T01/P04-T01/P05-T08 ownership; schema-reference registry.

### V632-R06 — Review A does not enumerate leaf checks; launch execution is incomplete

`docs/configs/review-a.v1.json:6` contains only `REVIEW_A_MECHANICAL`. That registry entry invokes `tools/run_review_a_checks.py --config review-config/review-a.v1.json`, the runner consuming the same configuration. It provides no leaf check set. A runner that iterates the list recurses; a runner that special-cases it must invent the missing check inventory.

P10-T01/T02 register only authorization issuance. Workspace preparation commands exist in the separate review registry but are not wired into those tasks' exact command lists, despite their declared workspace-attestation outputs. The configs freeze different output roots, but only a workspace prefix is specified; exact distinct workspace roots and mount destinations remain choices. Mechanical commands share the final runtime cwd, so an explicit namespace/mount mapping and launch chain are required to establish how those commands run within the two isolated workspaces.

The plan does improve trust requirements: an external Ed25519 key location, four-hour launch lifetime, one-hour aggregation window, one-use consumption, role distinction, peer-output exclusion and procedural fresh-session attestation are stated. Those policies do not supply the missing executable review graph. Review B also remains blocked by V632-R04.

Evidence: `docs/configs/review-a.v1.json`; `docs/registries/review-command-registry.v1.json:19`; `docs/registries/reviewer-role-registry.v1.json`; P10-T01/T02 exact command lists; `docs/contracts/05-reviewer-independence.md`.

### V632-R07 — Test discovery and harness compilation are promised, not frozen

P01-T01 names the configuration files and says that pytest includes all tests and `tsconfig.harness` includes harness/security/durability sources. It does not supply their exact configuration values or a complete source-to-command mapping. The only registered TypeScript compile command builds `tsconfig.test.json` at P04-T03; none compiles `tsconfig.harness.json` before the P03 IndexedDB child commands need its JS output.

The actual v6.2 baseline has `testpaths = ["tests/bootstrap"]`; its test tsconfig includes `src`, `test`, `test-red`, and `tools`, but not `test-harness`. Thus inherited configuration does not fill the omission. Python authoring tests, new security sources and the harness need exact discovery/compile commands, owners and ordering. No full runtime suite was run or claimed in this plan review.

Evidence: `docs/plans/p01-complete-artifact-materialization.md:75-76`; `docs/registries/task-command-registry.v1.json:94,744`; baseline `pyproject.toml` and `extension/tsconfig.test.json`.

### V632-R08 — BOOT0 verification accepts undeclared extracted files

Exact ZIP/sidecar paths, supplied bootstrap scripts and pre-authoring commands are present, resolving the earlier nonexistent-authoring-root assumption. But extraction does not require a new empty destination, and `verify_extracted_plan.py` checks only listed entries, not equality of the actual file set with the manifest. A disposable copy of this valid plan with an additional inert `unexpected.py` still returns a successful 79-entry verification receipt. `create_authoring_workspace.py` then copies the whole directory, ignoring only `.bootstrap`.

The initializer also records clean Git status before writing its new untracked repository receipt, so that recorded status does not describe the post-command state. The bundled bootstrap test checks only Python parsing. Freeze and verify extraction closure, source exclusions and the final receipt/cleanliness procedure; the current receipt can certify less than BOOT0 promises.

Evidence: `BOOTSTRAP.md:16`; `bootstrap/verify_extracted_plan.py:10`; `bootstrap/create_authoring_workspace.py:18`; `bootstrap/initialize_authoring_repository.py:16-17`. The supplied initializer and authoring-workspace creator were not executed.

### V632-R09 — Placeholder rejection and semantic verification are not established end to end

The supplied task schema accepts the actual manifest and rejects production authority and an empty rollback array. It accepts unknown/forward dependency IDs, a declared count of 60 with 59 tasks, and an extra unowned exact file. These are valid responsibilities for a planned semantic validator, and the plan does name those responsibilities; schema-only acceptance is not itself proof the plan is defective.

The concrete remaining hole is that the command schema accepts argv values `TBD`, `TODO`, `${COMMAND}` and `...`; it rejects only the tested angle-bracket placeholder. The P00 semantic-validation invocation takes the task manifest and schema, with no frozen binding to the command/ownership registries needed to close the cross-file checks. Those registries also have the ownership and sequencing defects above. Consequently, rejection by the schema-plus-semantic-validator pipeline cannot be verified from this contract. Specify the exact cross-file inputs and adversarial fixtures, and close the placeholder grammar.

Evidence: `docs/schemas/command-registry.schema.json:46`; P00-T03 and P02-T01 task contracts; `VERIFY_V632_P00_T03`; direct JSON Schema mutation checks recorded in `review-evidence.json`.
